# 14. Соглашения по коду

## Язык

- **Код, идентификаторы, JSDoc** — на английском.
- **Документация в `docs/`, README, TODO** — на русском.
- **Пользовательский текст в UI** — на русском.

## Структура импортов

Используем алиасы (`@core`, `@game`, `@rendering`, `@scenes`, `@ui`,
`@hooks`, `@utils`, `@assets`, `@audio`, `@physics`).

Порядок импортов:

1. Внешние библиотеки (`react`, `pixi.js`, `@pixi/react`).
2. Алиасные импорты (`@core/...`, `@game/...`).
3. Локальные относительные (`./Board`, `../scoring`).

ESLint + Prettier настроены, форматирование — `npm run format`.

## TypeScript

- **strict** включён.
- `any` запрещён в публичных API; для интеропа с Pixi/Matter допустим
  локально с комментарием `// any: <причина>`.
- Предпочитаем `type` для объединений и `interface` для объектов.
- Не используем `enum` — заменяем строковыми литералами или
  `as const`-объектами.

## React

- Функциональные компоненты + хуки.
- Без `React.FC` — типизируем `props` явно.
- Возвращаемый тип — `JSX.Element | null`.
- Селекторы Zustand: всегда конкретный селектор, не объект.

## Pixi

- `Container` для группировки, `Graphics` для процедурной графики,
  `Sprite` — для текстур.
- Стиль API: цепочки (`g.rect(...).fill({...}).stroke({...})`).
- Заводим **label** контейнеров для отладки (`g.label = 'tiles'`).

## Файлы и папки

- Папки в `kebab-case`, файлы — `PascalCase` для классов/компонентов и
  `camelCase` для модулей-функций.
- Не более одного export-default-а на файл. Предпочитаем именованные
  экспорты.

## Комментарии

- Объясняют **почему**, а не что.
- Доменные заметки помещаются прямо над функцией.
- Не повторяем имя функции в комментарии.

## Размер файла

- Стремимся к ≤300 строк. Большие модули — повод разбить.
- `BoardController` — исключение: он сознательно собирает оркестрацию
  в одном месте.

## Стейт

- Игровая модель — в `Board`/`gameMachine`. Не дублировать в Zustand.
- UI-стейт — в Zustand.
- События — в `bus` (mitt).

## Анимации

- Все tween-таргеты — Pixi-объекты (или их `scale`/`position`).
- Не анимировать через React-стейт игровые объекты.
- Запускать в `CommandQueue` всё, что должно быть последовательным.

## Ошибки

- `console.error` для багов, `console.warn` для нарушений ожиданий.
- Доменные функции не должны кидать — лучше возвращать `null` или
  `Result`-объект.

## Безопасность

- Не использовать `innerHTML` в DOM-оверлеях.
- Не доверять данным уровня из внешних JSON без валидации.

## Git

- `feat:`, `fix:`, `refactor:`, `docs:`, `chore:` — conventional commits.
- Один логический change на коммит.
- PR обязательно с описанием и чек-листом тестов.
